## IV. EXPERIMENTAL SETUP AND RESULTS

This section provides a technical analysis of the implemented multi-agent forecasting system using the GEFCom2014 load and solar benchmarks. Rather than treating forecasting as a single-model exercise, the evaluation emphasizes end-to-end behavior of an agentic pipeline: how data are validated and transformed, how optimization decisions are made and logged, how models are trained under consistent windowing constraints, and how human-in-the-loop post-processing modifies the operational forecast. The discussion is grounded in the system’s run artifacts under `logs/runs/<run_id>/` (including prediction files, plots, and the joint decision report) and in the implementation’s test suite, which reported all tests passing in the execution environment (17/17 passed).

### A. Data Engineering and Preparation Workflow

Experiments were conducted on the Global Energy Forecasting Competition 2014 (GEFCom2014) datasets for two tracks: load forecasting and solar power forecasting. The load track contains hourly demand measurements (in MW) and associated exogenous drivers, while the solar track contains hourly photovoltaic power targets with a set of weather-related predictors. Data were standardized into Parquet artifacts and indexed consistently by zone identifier and timestamp. A dataset manifest (`data/processed/dataset_manifest.json`) defines the artifact locations and column policies for each track, including feature columns, target columns, historical input columns, and future-known covariates used for multi-step forecasting.

At runtime, the PreparationAgent consumes the manifest and emits a staged readiness signal. The workflow is explicitly logged as a sequence of events: metadata collection (manifest path and track), validity checks (artifact existence and schema checks), column definition (target and covariate policies), and preference capture. This staged design is not only a software engineering convenience; it establishes a strict contract for downstream agents. If the manifest is missing required artifacts or if the data do not match the expected index structure, the agent publishes an error message rather than allowing the pipeline to proceed with ambiguous assumptions. Consequently, the preparation stage is fail-fast and observable, which is important when runs are repeated under different feature and optimization configurations.

When Table III feature search is enabled, the PreparationAgent performs dynamic feature construction and writes run-scoped prepared artifacts without modifying the canonical Phase-A outputs. Feature groups include calendar encodings, lagged sequences, correlation-selected variables, and optional interaction terms. A key representation decision concerns calendar time. Categorical encodings (for example, one-hot hour-of-day) can capture discontinuous operating regimes, but they increase dimensionality and impose sharp boundaries between adjacent times (notably between hour 23 and hour 0). Trigonometric encodings instead represent time as smooth cycles. In practice, trigonometric features provide a compact inductive bias for daily and weekly periodicities that are characteristic of load profiles, which can stabilize learning for models that prefer smooth feature spaces (for example, linear models, support vector regression, and gradient-boosted trees). Categorical features may still be useful when data show abrupt structural changes (for example, weekend schedules), but they typically require more data to estimate reliably; alternatively, trigonometric features preserve periodic structure with fewer parameters and reduce sparsity.

### B. Optimization Engine and Algorithm 1 Execution

Hyperparameter optimization is orchestrated by the ModelManagerAgent, which implements the batch Bayesian optimization logic described in Algorithm 1 using Optuna as the backend. The implementation follows an explicit ask-and-tell loop: the manager requests a batch of trial configurations, dispatches training directives, and updates the study state once results are returned. Multivariate sampling is enabled in Optuna’s TPE sampler, improving search efficiency when hyperparameters interact. This is operationally relevant because Table II contains settings whose effects are coupled (for example, the interaction between learning rate and model capacity in neural baselines, or between tree depth and learning rate in boosted trees).

The strict step constraints in Table II serve a practical purpose in stabilizing the search. For XGBoost, the number of estimators is sampled on a fixed grid (step size of 10). This discretization reduces sensitivity to minor changes that can produce near-duplicate trials while still consuming the optimization budget. Without a step constraint, adjacent trials can differ by only a few trees, leading to small metric differences dominated by noise and unstable downstream importance estimates. With discretization, each sampled configuration represents a meaningfully different model capacity, improving diversity within batched trials and producing clearer tradeoffs across the search trajectory.

Algorithm 1 execution is visible in the message stream. Each trial is associated with a correlation identifier and an Optuna trial number. The ModelManagerAgent emits telemetry that distinguishes observations (data readiness and returned metrics), decisions (whether to continue, stop, or publish importance), and actions (publishing the next batch of training commands). This separation is important for experimental analysis: it enables post hoc reconstruction of optimization dynamics and supports front-end rendering as a live sequence diagram rather than as opaque console output.

### C. Comparative Model Analysis Across Nine Families

The system supports nine model families spanning classical baselines and modern deep architectures: linear models, support vector regression, multilayer perceptrons, recurrent networks (LSTM and GRU), convolutional networks (CNN), gradient-boosted trees (XGBoost), and transformer backbones (PatchTST and iTransformer). This breadth is a deliberate design choice. Joint load and solar forecasting combines structured periodicity (load) with intermittent, weather-driven variability (solar), and the data are not expected to favor a single inductive bias across all regimes.

Baselines such as linear regression and support vector regression serve as fast reference points. They are sensitive to feature quality and therefore help isolate the contribution of Table III feature construction. When baseline performance improves after enabling feature search, the result indicates that representational choices, not only model complexity, are contributing to accuracy. These baselines are also computationally tractable under repeated trials, making them suitable for Algorithm 1 experiments on constrained hardware.

Neural baselines (MLP, LSTM/GRU, CNN) introduce additional capacity and can model nonlinear interactions between covariates and the target. However, their benefits depend on training stability and regularization, especially when the effective number of training windows is limited by the chosen horizon and stride. The framework addresses this by making early stopping and learning-rate configuration part of the trial plan and by logging epoch-level telemetry in research mode, enabling diagnosis of underfitting versus overfitting.

Transformer backbones, specifically PatchTST and iTransformer, are evaluated under the same window definition as the rest of the system to ensure a fair comparison. Their principal advantage is their ability to exploit long-range dependencies within the historical context without relying solely on hand-selected lag features. This property is particularly relevant for solar forecasting, where irradiance-related predictors and photovoltaic power can be influenced by evolving weather patterns across the day. CNNs can capture local motifs but typically require deeper receptive fields or carefully designed dilation to represent longer-range structure; alternatively, attention-based models can connect distant observations directly within the input window. In runs where solar variability is dominated by shifting cloud regimes and ramp events, transformer models are expected to align forecast ramps more accurately and recover more quickly from transient disturbances than models that primarily rely on local convolutions or fixed lag structures.

### D. Human-in-the-Loop Ablation and Deployment Adjustments

The DeploymentOperatorAgent implements a deployment-stage ablation in which forecasts can be adjusted using traceable rules aligned with the Table I taxonomy. The goal is not to arbitrarily improve metrics, but to provide an operational mechanism for incorporating late-arriving information under explicit governance. Adjustments can be global, hour-specific, or conditional based on predicted values or external indicators. The adjusted forecasts are stored alongside the original forecasts, and the applied rule is recorded as structured metadata, enabling direct before-and-after comparison within the same run.

A representative scenario illustrates the intended use. Consider a period in which the data show a systematic underprediction during the evening peak. An operator may know from external context that a heatwave is increasing demand and that load above a configured threshold should be upscaled. A practical rule is a conditional scaling that increases the forecast by 5 percent only when predicted load exceeds the threshold and only during peak hours. Such a rule corrects undershoot while preserving calibration in off-peak periods, where the original model may already be accurate. Operationally, this behaves as a “guard-railed” intervention: it applies only when a condition holds, it is logged and reversible, and it produces an explicit adjusted variant that can be compared against the original forecast.

This human-in-the-loop stage is integrated into the pipeline rather than being an external manual step. The decision is issued via an interactive gate or a chat command, translated into a structured directive, acknowledged by the deployment operator, and propagated into the integration report. The run artifacts therefore preserve not only the final adjusted predictions but also the rationale and scope of the adjustment.

### E. Metrics and Reporting Artifacts

Forecast quality is assessed using Root Mean Square Error (RMSE) and Mean Absolute Percentage Error (MAPE) over the multi-step horizon. RMSE measures absolute error magnitude in the target units (MW for load), while MAPE provides a relative error perspective that is informative across varying operating levels. For each run, the system exports predictions in a unified tabular format with aligned timestamps, horizon indices, and variant labels (for example, original versus adjusted). This standardization is essential for fair comparisons across model families and for consistent visualization in the workbench. The final joint report aggregates selected configurations, observed metrics, and deployment adjustments, yielding a reproducible experimental record suitable for both operational review and academic reporting.
